# gdb/QEMU 调试与保护层分析（2026-10-31 19:20）

## gdb 能用，而且已经用上了

- 宿主 gdb 18.1；QEMU 11.1.3 支持运行时开 gdbstub：
  HMP 命令 gdbserver tcp::1234，停止用 gdbserver none。
- gdb 能 attach 到整个 VM（4 个 vCPU 全部 halt），硬件断点（hbreak/Z1）可用，
  不需要先读内存，因此不受当前 CR3 限制。
- 关键用法：在 Smonitor 的计时器函数 0x458788 下硬件断点。每次命中都停在
  Smonitor 上下文，此时用 gdb 读 0x45883c 得到 "taskmgr.exe"，可确认上下文；
  随后用 RSP 的 m 包读取 0x46e000 区域，读到的是该进程当前的线性地址内容。
- 普通用户态地址在非目标上下文读会返回 E14（不可访问），所以必须靠断点命中目标进程。

## 用 gdb 抓到了什么

- 在 20 次计时器断点命中里，保护区 0x46e000-0x4c7000 每次都有 11 页与静态镜像不同；
  这些差异是稳定的运行期补丁（4-20 字节），形态为：
  push imm32; call 0x46ee55 之类的桩，指向一个分发器。
- 说明保护区不是“普通加密后整段执行”，而是按需解密 + 虚拟化分发：
  外部调用点被改写成桩，桩进入 0x46ee55 的分发器，真正逻辑由该层解释/调用。

## 原生高速采样器的收获

写了一个 C# 采样器（25 秒、21007 次整区读取），对每个字节记录任何时刻出现过的
非静态值并合并，得到 364544 字节里 361706 字节有过非静态值。合并结果里：

- 0x46e000 页是完整可读的 Delphi 窗体资源：
  DisplayName / Smonitor Service / OnStart / ServiceStart / TTimer / tmr1 /
  Enabled / Interval / OnTimer / tmr1Timer
  这证明该区包含被加密的资源数据，运行时确实被解密。
- 其余页是混合状态：部分页出现可读代码（例如 0x4795cc 处的 jmp 链），
  部分页仍是密文。说明不同页的解密时机/密钥状态不同，逐字节“最后非静态值”
  合并会混合多个状态，不能直接当明文用。

## 结论

保护层是“按需解密 + 自修改桩 + 虚拟化分发”的组合，不是简单 XOR/压缩。
要完整反混淆，下一步有两条现实路径：

1. 页级快照选择：重复整区采样，对每页保留“最像代码/数据的完整快照”（按熵、
   有效指令密度、是否为 55 8B EC 开头等打分），而不是逐字节合并；
2. 驱动受保护逻辑执行：先弄清 Student 到 Smonitor 的命令协议（端口会从 config
   的 mt 变化，当前为 63312；Windows 自带 pktmon 可抓 loopback），
   再用 U/V 命令把设备/保护开关打开，让受保护函数真正执行，然后用断点/采样
   在正确时机抓解密后的代码。
